Reading the notation

Yourdon–DeMarco for the data flow diagrams · UML 2.5 for the use cases

Four symbols carry the whole of sections 1–3. A process transforms data and is numbered so a lower level can decompose it — process 4.0 in the Level 1 diagram opens up as 4.1–4.7 in the Level 2 diagram. An external entity sits outside the system boundary: it is a source or a sink, never something the system stores. A data store is data at rest; a data flow is data in motion, and is named for what it carries, not for the verb that moves it.

External entity

A person or service outside the boundary. Employees, the three approvers, the mail relay.

Process

Numbered work the system performs. The number is its address across levels.

Data store

Data at rest — one or more database tables, or the file store on disk.

Data flow

Named data in motion. Every arrow says what travels, not merely that two things are connected.

01

Context Diagram — DFD Level 0

The whole system as one process, and everyone it exchanges data with

The context diagram fixes the scope: NexHRIS is a single process, and everything that talks to it is outside. Six external entities appear. Four are people — the Employee and the three approvers in the leave chain. Two are not: the campus mail relay, which carries one-time sign-in codes and status notices, and a public verifier — anyone who scans the QR code on a printed digital ID and reaches the public verification page without signing in.

The HR Administrator is drawn as a separate entity rather than a kind of employee because in this system it is a system account: it holds no leave, no ledger card and no Personal Data Sheet of its own.

02

Data Flow Diagram — Level 1

Process 0 opened up into eight processes and ten data stores

Level 1 explodes the single bubble of Figure 1 without adding or losing a single boundary flow — the diagram is balanced. What appears for the first time is the inside: the eight processes the campus actually performs, and the ten places data comes to rest.

Two things in this drawing are worth reading closely. First, D3 Blank Form Templates appears twice — once feeding PDS management, once feeding document rendering. A store drawn twice is the same store; the doubled left edge marks the repeat. It is repeated because the campus form is the source of truth in two different ways: as the file an employee downloads, and as the geometry the ledger card is rebuilt from. Second, D10 Document Store is a file system, not a table. Uploaded workbooks and their converted PDFs live on disk under storage/app; the database holds only the path and the metadata.

03

Data Flow Diagram — Level 2

Process 4.0 exploded — the leave application and approval chain

Only one Level-1 process is worth decomposing further, and it is the one the whole project was commissioned for: the leave chain that used to mean walking a printed form between three offices.

The single most important thing this diagram shows is the loop. A form returned at any stage does not resume where it stopped — it goes back to 4.2 and starts the chain again from the first approval. That is why 4.5 is drawn as its own process rather than as a branch inside 4.4: returning is a different transformation, not a different outcome of the same one.

The second thing worth noticing is that 4.3 sits between upload and approval. The chain is not a fixed sequence stored anywhere; it is derived per form from who applied, because nobody approves their own leave. A Dean’s form skips the Dean stage, and the Campus Director’s form goes to HR alone.

04

Use Case Diagram

UML 2.5 · four human roles, one abstract base actor, two secondary actors

Four roles share one interface; only their capabilities differ. Drawing that as four separate actors each wired to its own copy of “sign in” and “manage own profile” would produce a diagram nobody can read and a claim that is not true — those are the same use case. So the diagram uses actor generalization: an abstract System User owns what everyone can do, and each concrete role inherits it and adds its own.

Two inheritance decisions carry real information. Dean and Campus Director inherit from Employee, because they are members of staff who also file their own leave. HR Administrator inherits from System User instead — it is a system account, so it never files leave, holds no ledger card and submits no Personal Data Sheet. That single arrow is the whole reason the approval chain has to be derived per applicant rather than fixed.

Verify a digital ID hangs below the rest because it is the one use case reached without signing in at all: a QR code on a printed card resolves to a public page.

Where the boundary is enforced

A use case diagram states what a role may do; it does not by itself say where that is checked. In NexHRIS it is checked in the query, not the interface. A Dean’s visibility is scoped by User::scopeVisibleTo(), so a Dean who edits a URL to reach another college’s employee gets a 403 rather than data. Hiding the button was never the control.

05

Input — Process — Output

The capstone IPO chart, with the feedback path that makes it a cycle

The IPO chart answers a different question from the data flow diagrams. A DFD says where data goes; the IPO chart says what the system is for — what goes in, what happens to it, and what comes back out that the campus did not have before.

The feedback path along the bottom is not decoration. Three of this system’s outputs re-enter it as inputs: a returned leave form goes back to the employee to be corrected and re-uploaded, a corrected ledger line forces every balance below it to be replayed, and an unacknowledged policy stays on an employee’s list until they acknowledge it.
